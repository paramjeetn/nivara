## 1. Executive Summary & Objective

### 1.1 Objective
The core objective of Step 6 is: **"One engine, many facility types, with service constraints encoded."**  

Prior to Step 6, Nivara operated against hardcoded facility metadata dictionaries and assumed uniform operational flexibility across all assets. In critical real-world deployments—especially healthcare campuses, continuous manufacturing estates, and institutional data infrastructure—energy optimization can never be unconstrained. Curtailing an air-handling unit in an academic classroom causes mild discomfort; curtailing an air-handling unit in an **Operating Theatre (OT)** or **Intensive Care Unit (ICU)** risks patient life. Similarly, power interruptions to cold-chain vaccine refrigeration or continuous industrial process drives result in catastrophic financial, clinical, and safety losses.

Step 6 encodes these critical distinctions directly into the platform architecture:
1. **Pydantic Schema & Dynamic Loader (`src/campus_energy/profiles.py`):**  
   Established strongly typed models for `ComfortBound`, `ProtectedLoad`, and `FacilityProfile`, supported by discovery loaders (`load_facility_profile`, `load_all_profiles`) and flexible lookup dictionaries (`ProfileDict`).
2. **Canonical Profile Declarations (`config/facility_profiles/` and `configs/facility_profiles/`):**  
   Configured four standard institutional facility types with explicit non-curtailable protected loads, strict ASHRAE/NABH comfort bounds, utility tariff classes, and statutory compliance frameworks:
   - **University** (Vidya Institute of Technology, 12,000 m²)
   - **District Hospital** (Rajiv Gandhi District Hospital, 8,500 m²)
   - **Government Office** (Collectorate Complex, 5,200 m²)
   - **Industrial Campus** (Kalinga Industrial Estate, 18,000 m²)
3. **Interactive Dashboard Modernization (`src/campus_energy/dashboard/app.py`):**  
   Replaced static facility dictionaries with dynamic profile discovery, surfacing protected load counts and compliance frameworks in the sidebar, and rendering standard `🛡️ Protected Load: Non-Curtailable` badges across the **3D Campus Map**, **AI Alerts**, **Asset Explorer**, and **Governance & Policy** modules.
4. **Comprehensive Test Suite Expansion (`tests/test_facility_profiles.py`):**  
   Added 7 rigorous unit tests validating profile schemas, hospital clinical load non-curtailability, asset protection lookup semantics, comfort bound fallback logic, backwards-compatible dict indexing, and a synthetic "Fifth Facility" test demonstrating plug-and-play profile extensibility without code modifications.

## 3. Architectural Specification & Data Models

### 3.1 Pydantic Schemas (`src/campus_energy/profiles.py`)

#### `ComfortBound`
Defines operational boundaries for occupant thermal comfort and air handling setpoint optimization:
```python
class ComfortBound(BaseModel):
    min_pmv: float = Field(description="Minimum Predicted Mean Vote (PMV) lower comfort limit")
    max_pmv: float = Field(description="Maximum Predicted Mean Vote (PMV) upper comfort limit")
    temp_min_c: float = Field(description="Minimum acceptable temperature in Celsius")
    temp_max_c: float = Field(description="Maximum acceptable temperature in Celsius")
```

#### `ProtectedLoad`
Encodes mission-critical electrical or thermal assets that cannot be curtailed or shed:
```python
class ProtectedLoad(BaseModel):
    asset_id: str = Field(description="Unique asset identifier matching telemetry/asset registries")
    asset_name: str = Field(description="Human-readable asset description")
    zone_id: Optional[str] = Field(default=None, description="Physical zone containing the asset")
    category: str = Field(
        description="Criticality class: 'life_safety', 'cold_chain', 'critical_it', 'research_lab', 'continuous_process'"
    )
    curtailable: bool = Field(
        default=False,
        description="Whether this load can be curtailed or shed during peak shaving / demand response"
    )
    min_power_kw: Optional[float] = Field(
        default=None,
        description="Absolute minimum operational electrical power in kW"
    )
    reason: str = Field(
        description="Defensible clinical, safety, regulatory, or operational reason for non-curtailability"
    )
```

#### `FacilityProfile`
Canonical institutional profile tying together physical, operational, and regulatory parameters:
```python
class FacilityProfile(BaseModel):
    facility_id: str
    facility_name: str
    facility_type: str
    location: str
    floor_area_m2: float
    peak_occupancy: int
    data_dir: str
    comfort_bounds: dict[str, ComfortBound]
    protected_loads: list[ProtectedLoad]
    tariff_profile: str
    compliance_frameworks: list[str]
    default_roles: list[str]
    icon: str = "🏢"
    config: Optional[str] = None
```

### 3.2 Key Helper Methods on `FacilityProfile`

1. **`is_asset_protected(asset_id: str) -> bool`**:  
   Performs fast, case-insensitive lookup against `protected_loads`. Returns `True` if the asset is protected.
2. **`get_protected_load(asset_id: str) -> Optional[ProtectedLoad]`**:  
   Retrieves the full `ProtectedLoad` record, enabling inspection of `category`, `min_power_kw`, and `reason`.
3. **`get_comfort_bound_for_zone(zone_type: str) -> ComfortBound`**:  
   Resolves zone thermal bounds using multi-tiered matching: exact match $\to$ case-insensitive match $\to$ substring/alias matching $\to$ general/fallback bounds.
4. **`__getitem__(item: str)` and `get(item: str)`**:  
   Provides dictionary-like subscription (`profile["key"]`, `profile["data_dir"]`, `profile["floor_area_m2"]`), allowing seamless interoperability with legacy dashboard and governance routines expecting dictionary payloads.

## 8. Strategic Bridge to Step 7 (Service-Impact Guard)

Step 6 lays the foundational data contract for **Step 7: Service-Impact Guard**.

In Step 7:
1. **Automated Interception of Load Curtailment:**  
   The autonomous dispatch and demand-response optimizers will query `profile.is_asset_protected(target_asset_id)`. If `True`, the action will be strictly blocked or intercepted with error code `ERR_PROTECTED_LOAD_CURTAILMENT_REJECTED`.
2. **Thermal Setpoint Envelope Clamping:**  
   HVAC drift and setback routines will call `profile.get_comfort_bound_for_zone(zone_type)`. If proposed setpoints exceed the `[temp_min_c, temp_max_c]` or `[min_pmv, max_pmv]` ranges (such as during hospital surgery hours or intensive care), the guard will clamp setpoints to safe boundaries.
3. **Minimum Power Guarantees:**  
   Optimizers attempting to throttle power will respect `protected_load.min_power_kw`, ensuring continuous operation of critical chillers, cleanroom fans, and life-safety systems.
